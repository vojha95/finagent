# E3 retrieval labelling (Phase 7.5)

Blueprint 10.3: hand-mark the passages that explain each signal, then compare the four retrieval
variants. **7.5 builds the labelling sheet only.** E3 is scored in 7.6. E4 (card faithfulness)
follows once E3 has picked a variant, so its cards come from the final system.

## 1. Query selection rule (written 2026-11-25, before any retrieval ran on the test companies)

The rule is fixed in `configs/e3.yaml` and implemented in `finagent/evaluation/e3.py`
(`select_signals`, `select_explains`). It reads the signal results and the statement set only,
never a retrieval result.

- **Companies:** the six test companies, which are the validation split without the dev
  companies (D10: AMZN and MSFT), in `configs/universe.yaml` order. No held-out company is run.
  Each company gets 5 queries: 3 signal queries and 2 explain queries, so 30 in all.
- **Signal queries:**
  - **Candidates:** every FIRED (fiscal year, signal) of `runs/insights-0002/signals.csv`, over
    all years, except the signals on model data (R10, model-derived).
  - **Selection:** in 3 rounds, each company in order takes one candidate. It takes the signal
    chosen the fewest times so far across all companies. Ties go to the fiscal year this company
    has used the fewest times, then the latest fiscal year, then the signal's order in
    `configs/signals.yaml`.
- **Explain queries:**
  - **The movement:** the latest fiscal year filed by as_of, as `explain_movement` reads it.
  - **Metrics:** company k (0-based) takes the two metrics of (revenue, operating_income,
    operating_cash_flow) other than the one at k mod 3, so each metric is used 4 times.
  - **When a movement cannot be searched** (the tools return a GAP before any search): the
    company's remaining metric replaces it. If the company is still short, it takes one more
    signal by the rule above.
- **What the sheet shows** for each query, in plain words with the numbers and the year:
  - a signal: the card's own text without its evidence line;
  - an explain query: "Revenue increased from USD …m in FY… to USD …m in FY… (+…%)", from the
    accepted values.
- **What is searched:** the product's query, the same for every variant:
  - a signal: its frozen query (`configs/query_templates.yaml`) over Items 7 and 8 with notes;
  - an explain query: the explain template with the direction, over Item 7;
  - in both cases, in the 10-K of the query's fiscal year, as of 2026-11-24.

**How the rule applied** (`python -m finagent.evaluation.e3 queries`; the table is in section 5):

- **Signals:** 18 queries covering 9 signals: R1 3, R2 3, R3 1, R4 2, R5 2, R6 2, R7 2, R8 2,
  R9 1. Every selected signal is evaluated again as of 2026-11-24 and must still be FIRED.
  - The rule gave four companies the same signal in two years: NKE R1, T R5, CL R7, ABT R2.
    Each repeat is a different 10-K. It is kept as chosen (#239).
- **Explain:** CVX and MRK FY2025 operating income return GAP NOT_REPORTED, because neither
  reports an operating income subtotal. Revenue replaced it for both (#238). The metrics are
  therefore revenue 5, operating cash flow 5, operating income 2. No company was short.

## 2. Pool and sheet

- **Pool:**
  - All four variants (bm25, dense, hybrid_rrf, hybrid_rrf_rerank) run with the same as_of and
    sections, and each contributes its top 5 chunks.
  - Duplicates are removed, and each query's chunks are shuffled with a fixed seed.
  - The product's hybrid_rrf_rerank keeps 3. For the pool, its reranked list is read to 5, and
    the key records every rank, so 7.6 can score it at 3 or at 5 (#236).
- **What stays hidden:**
  - The sheet hides the variant, the rank and the score.
  - `gold/e3_pool_key.jsonl` maps each chunk to the variants and ranks that found it. Do not open
    it while labelling.
- **Labels:** 2 = explains the movement, 1 = partly, 0 = does not. There is also one "better
  passage" cell per query, for a filing sentence that explains the movement but is not in the
  pool.
- **Labelling against the statement:** the sheet shows the plain-words statement. The variants
  search the product's query (#240). The question for each passage is: does it explain this
  movement, in this filing?
- **Sheet columns:** query_id, company, fiscal_year, query, row, section, passage, label
  (dropdown 0/1/2), notes, better_passage (one cell merged down each query's rows), chunk_id.
  - `row` is the shuffled position, not a rank.
  - `chunk_id` names the filing, section and chunk number. Import needs it. It says nothing
    about the variants.
  - Panes are frozen at E2.
  - Some chunks are short, such as a note heading of 4 words. They are labelled as they are.
- **Worked examples** (instructions tab, dev companies only, the builder's labels; #241):
  - AMZN FY2025 operating income, Item 7: label 1.
  - MSFT FY2025 R3, Item 7: label 2.
- **Completeness:** every variant returned 5 chunks for every query (120 lists filled to rank
  5). This check read the key for counts only, never for which variant found which chunk.
- **Commands:**
  - `python -m finagent.evaluation.e3 validate --partial` checks progress.
  - `validate` checks a finished sheet.
  - `import` writes `gold/e3_labels.jsonl`, one record per query: its labels, notes, better
    passage, and the pool file's sha256. Import refuses a sheet with any error or any unlabelled
    row.
  - Errors checked: wrong header; a row not in the pool; duplicate or missing rows; an edited
    passage; a label other than 0, 1 or 2; a better passage outside the query's merged cell.

## 3. Limitation: pooled judgements

Only pooled chunks are judged: the union of the four variants' top 5. A passage that no variant
ranked in its top 5 is never labelled, unless Vineet pastes it as a "better passage".

**Recall@5 in 7.6 is therefore relative to the pool, not to the whole filing.** It can overstate
every variant's true recall, and it favours the variants that built the pool. This is a known
limitation of pooled evaluation, recorded here and in the issue log (#237).

The "better passage" cells give a partial check: a query with a better passage and no label-2
chunk in the pool shows a passage that every variant missed.

## 4. Scoring rule (7.6; written 2026-11-25 before any score was computed)

Written after Vineet's labels were imported (gold/e3_labels.jsonl, 495aa54) and before the
variant key (gold/e3_pool_key.jsonl) was joined to them. The parameters are in `configs/e3.yaml`
`scoring`; `python -m finagent.evaluation.e3 score` applies them.

- **Ranked lists:** for each query and variant, the chunks the key gives that variant at ranks
  1-5. **Every variant is scored at depth 5**, hybrid_rrf_rerank included (its reranked list read
  to 5, as in the pool; #236, #243). The product keeps 3 reranked quotes; that is not changed.
- **Relevance:**
  - **primary (lenient):** label >= 1 (explains or partly explains the movement);
  - **secondary (strict):** label = 2.
- **Pool misses:** a "better passage" (E3-Q19) explains the movement but is in no variant's top
  5. It counts as **one relevant passage under both definitions that no variant found**. It adds
  1 to the query's relevant count, the Recall@5 denominator, and is never found; it does not
  change MRR@5. Every pool miss is reported.
- **Per query and variant:**
  - **Recall@5** = relevant passages in the variant's top 5 / all relevant passages of the query
    (the pooled ones that meet the definition, plus pool misses);
  - **MRR@5** = 1 / rank of the first relevant passage in the variant's top 5, or 0 if there is
    none.
- **Means** over the queries with at least one relevant passage under the definition. **Queries
  with none are left out of that definition's means and counted separately.**
- **Intervals:** 95% percentile bootstrap over queries (the scored queries resampled with
  replacement; 2,000 draws, seed 0).
- **Against bm25:** a paired bootstrap of the MRR@5 difference (variant minus bm25), with the
  same resampled queries for both, 2,000 draws, seed 0, a 95% percentile interval. It is reported
  for both definitions.
- **Default switch rule (primary MRR@5 only):** the default (configs/retrieval.yaml
  `default_variant`, today bm25) moves to another variant only if that variant's primary MRR@5
  beats bm25's with a paired 95% interval that excludes zero (lower bound > 0). If several
  qualify, the cheapest by runtime wins: mean ms per query in retrieval-0003 (bm25 45, dense 58
  with a warm cache, hybrid_rrf 59, hybrid_rrf_rerank 383). Otherwise bm25 stays. No other
  measure (Recall@5, the strict definition, a company or query kind) can move the default. If
  hybrid_rrf_rerank were chosen, the product would keep its 3 quotes.
- **Breakdowns (report only):** per company and per query kind (signal vs explain), the same
  means with intervals and n.
- **Recorded** as e3-0001 in eval/experiments.csv. Recall@5 is relative to the pool (section 3,
  #237).
